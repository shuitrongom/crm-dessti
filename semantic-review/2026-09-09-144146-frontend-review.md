# Frontend review — crm-anuncios-luminosos (Angular 21, zoneless, signals-first)

The frontend is a large, multi-scope Angular 21 app (plataforma / empresa / portal) built standalone, signals-first, with a shared component kit (StateContainer, DataTable, ConfirmDialogService, NotificacionesService, PageHeader, ProgressBadge, IndicatorCard) and a deny-by-default auth model. Overall the engineering quality is high: every one of the 34 feature HTTP services maps to a real backend controller under `/api/v1`, the documented integration gaps (no `GET /usuarios`, no `/roles` controller, complementos de pago via CxC) are handled honestly instead of faked, RFC7807 errors go through a single `mensajeDeError` helper, and destructive/state-change flows consistently gate on `ConfirmDialogService` and atomic permissions. The problems that remain are the kind parallel agents produce: a missing app-wide locale registration that makes several currency/number screens throw at render time, and three pairs of overlapping services/models plus one dead route file that will drift.

Watch for:
- **[confirmed] Missing `es-MX` locale registration** — every view that pipes `currency: 'MXN' : … : 'es-MX'` or `number: … : 'es-MX'` throws `NG0701 / Missing locale data for the locale "es-MX"` at render. `app.config.ts` never calls `registerLocaleData`. This is a runtime blocker on tesoreria, rhnomina, presupuestos, reportes/inteligencia (and any currency screen).
- **[confirmed] Duplicated Tablero / Estrategia / Presupuestos services + models** across `features/empresa/**` and the `-vistas` / `reportes` feature modules — same endpoints, duplicated DTO interfaces, already drifting (`Indicador` vs `IndicadorTablero`).
- **[confirmed] Dead route file** `portal/portal-vistas.routes.ts` (`portalVistasRoutes`) is never imported; its routes are already inlined in `portal.routes.ts`.
- **[confirmed] Two admin routes without a per-permission guard** (`roles`, `configuracion`) while every sibling route has one.

**Verdict**: NEEDS_CHANGES

## High-level view

The locale gap is the one true blocker. Angular ships only `en-US` locale data; the app passes `'es-MX'` as the explicit locale argument to `currency`/`number` pipes in many templates but never registers `localeEsMx` nor sets a `LOCALE_ID`/`DEFAULT_CURRENCY_CODE` provider. The project builds fine (locale resolution is a runtime concern) which is exactly why this slipped through — it only fails when a Spanish-locale pipe actually renders. A single `registerLocaleData(localeEsMx)` + provider in `app.config.ts` fixes every screen at once and lets the templates drop the repeated `'es-MX'` argument.

The zoneless setup is correct and needs no change: Angular 21's `bootstrapApplication` installs zoneless change detection by default (`provideZonelessChangeDetectionInternal`), so the absence of `provideZonelessChangeDetection()` and of zone.js is intentional and works. The signals-first discipline is real — `input()`/`output()`, `signal`/`computed`, `inject()`, `@if`/`@for` with `track` everywhere, no NgModules, no `*ngIf`/`*ngFor`, no `effect()` misused for derivation. The one-shot HTTP `subscribe()` calls are not leaks because those observables complete after a single emission.

The duplication is the parallel-work signature. One agent built thin "admin entry point" services under `features/empresa/**` (Tablero, Estrategia, Presupuestos) while another built the full feature modules (`reportes`, `estrategia-vistas`, `presupuestos-vistas`) that supersede them. The result is two `TableroService` classes hitting `GET /reportes-bi/tablero` with duplicate `FiltroTablero`, two estrategia services over `/estrategia/*` with duplicate request/DTO types, two presupuestos services, and two `Tablero` model shapes whose indicator interface names have already diverged. This is drift-prone, not merely redundant.

Security gating is sound and deny-by-default: nav items and route guards check `tienePermiso`/`tieneRol`, the portal never sends `clienteId` (the backend scopes it), and all nav permissions correspond to permissions actually seeded in the DB (verified against `V5`/module migrations), so there are no dead never-visible menu entries. The one wrinkle is that two admin routes rely only on the coarse `admin_empresa` role guard and skip their fine-grained `guardaPorPermiso`, unlike their siblings — a consistency gap rather than an open door, since the backend re-imposes authorization.

Per-domain enums, state machines (`TRANSICIONES_ESTADO_OF`, `TRANSICIONES_ESTADO_OTI`, etc.), and `ETIQUETA_ESTADO_*` maps are legitimately separate and should stay that way; collapsing them into a generic util would be over-abstraction. The shared `finanzas-comun/tono-estado` (tono + humanizar) and `shared/models/estado-solicitud` are good consolidation already in place.

### The es-MX locale black hole

`app.config.ts` providers are `provideBrowserGlobalErrorListeners`, `provideRouter`, `provideHttpClient`, `provideAnimationsAsync` — no locale registration. Angular bundles only `en-US` locale data; any other locale must be registered with `registerLocaleData`. Templates across the app pass `'es-MX'` as the explicit locale to the pipe, e.g.:

```html
{{ m.monto | currency: 'MXN' : 'symbol-narrow' : '1.2-2' : 'es-MX' }}   <!-- tesoreria/movimientos -->
{{ r.neto  | currency: 'MXN' : 'symbol-narrow' : '1.2-2' : 'es-MX' }}   <!-- rhnomina/nomina -->
{{ indicador.valor | number: '1.0-2' : 'es-MX' }}                        <!-- reportes/inteligencia -->
{{ v.ingresosEstimados | currency: 'MXN' : … : 'es-MX' }}                <!-- presupuestos-vistas -->
```

When a pipe is given a locale whose data isn't registered, Angular throws `NG0701: Missing locale data for the locale "es-MX"` while rendering that view — so tesoreria, rhnomina, presupuestos, reportes/inteligencia and every other currency/number screen fail the moment they display data. The build passing (verified: `ng build` completes) is misleading because locale resolution happens at runtime, not compile time.

Fix in one place:

```ts
// main.ts or app.config.ts
import { registerLocaleData } from '@angular/common';
import localeEsMx from '@angular/common/locales/es-MX';
registerLocaleData(localeEsMx);

// app.config providers
{ provide: LOCALE_ID, useValue: 'es-MX' },
{ provide: DEFAULT_CURRENCY_CODE, useValue: 'MXN' },
```

With `LOCALE_ID` set app-wide, the templates can drop the trailing `: 'es-MX'` argument entirely (it becomes the default), which also removes the repetition. This is the single most important change in the review.

Note on zoneless (not a bug): there is no `provideZonelessChangeDetection()` and no zone.js in `angular.json`/`package.json`. In Angular 21 this is correct — `bootstrapApplication` injects zoneless change detection by default (confirmed in `@angular/core` where `allAppProviders` begins with `provideZonelessChangeDetectionInternal()`). No action needed.

### Parallel-agent service/model duplication

Three domains have two services each because the "admin entry point" and the "business vistas" module were built independently:

```
GET /reportes-bi/tablero
  ├── features/empresa/services/tablero.service.ts   (TableroService, FiltroTablero, Tablero from home.models)
  └── features/reportes/services/tablero.service.ts  (TableroService, FiltroTablero, Tablero from reportes.models)

/estrategia/esencia, /estrategia/objetivos
  ├── features/empresa/services/estrategia.service.ts        (EstrategiaService — subset)
  └── features/estrategia-vistas/services/estrategia-vistas.service.ts  (EstrategiaVistasService — superset)

/presupuestos
  ├── features/empresa/administracion/services/presupuestos.service.ts  (PresupuestosService — listar only)
  └── features/presupuestos-vistas/services/presupuestos-vistas.service.ts (PresupuestosVistasService — superset)
```

The drift is already visible: the two `Tablero` models are structurally the same but their indicator interface is named `IndicadorTablero` in `empresa/home/home.models.ts` and `Indicador` in `reportes/models/reportes.models.ts`, so a backend field change has to be edited in two shapes and the two will silently diverge. `GuardarEsenciaRequest`, `CrearObjetivoRequest`, `EsenciaEmpresa`, `ObjetivoEstrategico`, and `Presupuesto` are likewise each defined twice. Recommend one canonical service+model per domain (the `-vistas`/`reportes` versions are the fuller implementations); have the `empresa/**` admin screens import those instead of maintaining their own copies.

### Dead portal route file

`portal/portal-vistas.routes.ts` exports `portalVistasRoutes` with five routes (cotizaciones, pruebas-diseno, proyectos, tickets, facturas). A grep for `portalVistasRoutes` finds only its own declaration — nothing imports it. The same five routes are already declared as children of the ShellLayout in `portal.routes.ts`, which is what `app.routes.ts` actually loads. So the file is dead code that duplicates live routing; if the live copy changes, this one won't, and a future reader may wire up the stale one. Either delete it, or refactor `portal.routes.ts` to spread `...portalVistasRoutes` as its children so there's a single source.

### Auth gating: solid, with one consistency gap

The permission model is clean: `AuthService.tienePermiso(recurso, operacion)` is deny-by-default, `NavigationService` filters every menu item by a `visible(auth)` predicate, and route guards (`guardaPorPermiso`, `guardaPorRoles`) redirect to `/acceso-denegado`. I cross-checked every nav permission against the DB seeds (`V5` catalog plus module migrations) — `objetivo_estrategico:listar`, `tablero:leer`, `inteligencia_negocio:leer`, `bandeja:leer`, `analitica_social:leer`, `reporte_financiero:leer`, `almacen:listar`, etc. all exist, so there are no dead never-visible entries. The portal correctly never sends `clienteId`; the backend `PortalClienteController` scopes by the authenticated client.

The gap: in `administracion.routes.ts`, `usuarios`/`sesiones`/`branding`/`estrategia`/`presupuestos` each carry a `guardaPorPermiso(...)`, but `roles` and `configuracion` carry none — they inherit only the coarse `guardaAdminEmpresa` (role check). A deep link to `/empresa/administracion/roles` loads without a permission check. It's low severity because the `roles` view only renders the user's own JWT claims (no privileged data, no fake endpoint) and the backend re-imposes authorization on any real call, but for consistency both routes should get the matching `guardaPorPermiso` (`rol:leer`, `empresa:cambiar_estado`).

### Documented gaps are honest, not black holes

The prior agents' documented gaps check out as real and gracefully handled:
- `UsuariosService` has no `listar()` because the backend exposes no `GET /usuarios`; the file documents this and offers alta/desactivar/roles by identifier instead of silently no-oping.
- `AdminRoles` renders the authenticated user's roles/permissions from the token and states in a comment that no `/roles` controller exists yet (confirmed: no `RolController` among the backend REST adapters). It doesn't pretend to CRUD roles.
- Contabilidad reports are limited to `ingresos`/`iva`/`libro-polizas` and complementos de pago flow through CxC — matching `ReportesFinancierosController` and `PagoClienteController`. No invented endpoints.

Every `api.url('…')` path I extracted from the 34 services resolves to a real controller mapping; no undocumented fake endpoint was found.
