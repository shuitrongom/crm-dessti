Resumen de arquitectura

IIS actúa como proxy inverso delante de la aplicación. Recibe el tráfico HTTPS del navegador, termina TLS, sirve la aplicación de Angular (SPA) en la raíz / y reenvía las peticiones a /api hacia el backend de Spring Boot, que escucha solo en la interfaz local por HTTP. El backend nunca se expone directamente a Internet.

Navegador (tester) │ HTTPS · TLS 1.2+ · puerto 8056 │ https://dessti-aplicaciones.ddns.net:8056 ▼ ┌─────────────────────────────────────────────────────────────┐ │ IIS (Windows Server) — Proxy inverso │ │ • Termina TLS con el certificado del dominio │ │ • Sirve la SPA de Angular en / (archivos estáticos) │ │ • Enruta /api → backend (URL Rewrite + ARR) │ │ • Añade X-Forwarded-Proto=https / Host / For │ └─────────────────────────────────────────────────────────────┘ │ HTTP interno (solo localhost) + cabeceras X-Forwarded-* │ http://127.0.0.1:8080 ▼ ┌─────────────────────────────────────────────────────────────┐ │ Backend Spring Boot (Java 21, Tomcat embebido) │ │ • context-path /api/v1 │ │ • Autenticación stateless con Bearer JWT (sin CSRF) │ │ • Migraciones Flyway al arrancar │ └─────────────────────────────────────────────────────────────┘ │ JDBC (localhost:5432) ▼ ┌─────────────────────────────────────────────────────────────┐ │ PostgreSQL 17 — base "dessti_plataforma" │ │ • Rol migrador (DDL, BYPASSRLS) para Flyway │ │ • Rol de aplicación (RLS activa) para el runtime │ └─────────────────────────────────────────────────────────────┘
Puntos clave
  • El frontend usa la base de API relativa /api/v1 (mismo origen), por lo que no requiere recompilarse para el servidor.
  • El backend confía en las cabeceras X-Forwarded-* gracias a --server.forward-headers-strategy=framework, así reconstruye URLs https:// y emite HSTS coherente.
  • El puerto interno del backend (8080) no debe abrirse en el firewall.

Requisitos previos en el servidor

Verifica cada requisito antes de comenzar. Usa PowerShell como Administrador.

1. Windows Server con permisos de administrador

Inicia sesión con una cuenta con privilegios de administrador local. Abre PowerShell con «Ejecutar como administrador».

2. IIS instalado

Comprueba que el servicio web (W3SVC) está presente y en ejecución:

# ¿Está instalado y corriendo IIS?
Get-Service W3SVC
# Si falta, instálalo (rol Web Server):
Install-WindowsFeature -Name Web-Server -IncludeManagementTools

3. Módulos URL Rewrite y ARR (Application Request Routing)

URL Rewrite reescribe rutas; ARR es lo que habilita el proxy inverso (permite que IIS reenvíe peticiones a otro servidor HTTP, en este caso el backend local). Ambos se instalan con el Web Platform Installer o descargándolos desde el sitio de IIS de Microsoft.

Habilita el proxy en ARR (imprescindible) Sin esto, el reenvío de /api devolverá error. En el Administrador de IIS: selecciona el nodo del servidor (raíz, no el sitio) → doble clic en Application Request Routing Cache → panel derecho Server Proxy Settings… → marca Enable proxy → Apply.

Para verificar que los módulos están registrados:

# Lista módulos globales; busca "RewriteModule" y "ApplicationRequestRouting"
& "$env:windir\system32\inetsrv\appcmd.exe" list modules

4. Java 21 (JDK) instalado y en el PATH

# Debe reportar la versión 21
java -version

Si el comando no se reconoce, instala un JDK 21 (por ejemplo, Temurin/Adoptium u Oracle) y agrega su carpeta bin al PATH del sistema. Anota la ruta a java.exe; la necesitarás en el Paso 5.

5. PostgreSQL instalado (versión 17 recomendada)

# ¿Está el servicio de PostgreSQL en ejecución? (el nombre suele incluir la versión)
Get-Service *postgres*
# Versión de la herramienta de línea de comandos
psql --version

Asegúrate de recordar la contraseña del superusuario postgres (la definiste al instalar). La necesitarás para crear la base y los roles en el Paso 1.

Paso 1 Base de datos (PostgreSQL)

Crea la base dessti_plataforma y dos roles con privilegios separados (Req 23): un rol migrador que es dueño del esquema y puede saltarse RLS solo para migrar, y un rol de aplicación con RLS siempre activa para el runtime.

Abre una consola psql como superusuario:

# Conéctate como el superusuario "postgres"
psql -U postgres -h 127.0.0.1

Ejecuta el siguiente script SQL (sustituye los placeholders por tus claves reales):

-- 1) Rol MIGRADOR: dueño del esquema, con DDL y BYPASSRLS (solo para migrar)
CREATE ROLE dessti_migrator WITH LOGIN PASSWORD '[CLAVE_MIGRATOR]' BYPASSRLS;

-- 2) Rol de APLICACIÓN: runtime del backend, SIN superusuario y SIN BYPASSRLS
--    (la Row-Level Security SIEMPRE aplica al tráfico de negocio)
CREATE ROLE dessti_app WITH LOGIN PASSWORD '[CLAVE_APP]' NOSUPERUSER NOBYPASSRLS;

-- 3) Base de datos, propiedad del rol migrador
CREATE DATABASE dessti_plataforma OWNER dessti_migrator;

-- 4) Permisos de conexión del rol de aplicación
GRANT CONNECT ON DATABASE dessti_plataforma TO dessti_app;

-- 5) Conéctate a la nueva base para ajustar privilegios de esquema
\c dessti_plataforma

-- El esquema public queda como área de trabajo del migrador
ALTER SCHEMA public OWNER TO dessti_migrator;
GRANT USAGE ON SCHEMA public TO dessti_app;

-- Privilegios por defecto: lo que cree el migrador será usable por la app
ALTER DEFAULT PRIVILEGES FOR ROLE dessti_migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO dessti_app;
ALTER DEFAULT PRIVILEGES FOR ROLE dessti_migrator IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO dessti_app;
Flyway crea el esquema al arrancar No necesitas crear tablas a mano. Al iniciar el backend, Flyway aplica las migraciones (con el rol migrador) y siembra los datos de plataforma (roles predefinidos, permisos, catálogos). El rol de aplicación consulta después con RLS activa.
No uses las claves de desarrollo [CLAVE_MIGRATOR] y [CLAVE_APP] deben ser contraseñas nuevas y robustas, exclusivas de este servidor.

Paso 2 Backend (jar + argumentos)

  1. Crea las carpetas de instalación y de logs: 
    New-Item -ItemType Directory -Force -Path C:\apps\crm\backend
New-Item -ItemType Directory -Force -Path C:\apps\crm\logs
  2. Copia el artefacto del backend a la carpeta de instalación: 
    Copy-Item ".\crm-0.0.1-SNAPSHOT.jar" "C:\apps\crm\backend\"

    El artefacto se genera en backend/target/crm-0.0.1-SNAPSHOT.jar tras compilar. Cópialo desde tu equipo de build al servidor.

Paso 3 Frontend (SPA + web.config)

  1. Crea la carpeta del sitio: 
    New-Item -ItemType Directory -Force -Path C:\inetpub\wwwroot\crm
  2. Copia el contenido de la carpeta browser del build (no la carpeta, sino lo que hay dentro: index.html, los .js, .css, etc.): 
    # Desde tu equipo de build, el origen es frontend\dist\frontend\browser
Copy-Item ".\dist\frontend\browser\*" "C:\inetpub\wwwroot\crm\" -Recurse -Force
  3. Coloca el web.config de este paquete en la raíz del sitio: 
    Copy-Item ".\web.config" "C:\inetpub\wwwroot\crm\web.config" -Force
Sobre la base de API relativa La SPA llama a /api/v1 en el mismo origen. IIS reenvía esas llamadas al backend (regla del web.config). Por eso no hace falta recompilar el frontend para el servidor.
Verifica el contenido copiado En C:\inetpub\wwwroot\crm debe existir index.html directamente (no dentro de una subcarpeta browser). Si ves una subcarpeta browser, copiaste la carpeta en vez de su contenido.

Paso 4 IIS: sitio, TLS, ARR y firewall

4.1 Crear el sitio "CRM"

En el Administrador de IIS: clic derecho en Sitios → Agregar sitio web…

  • Nombre del sitio: CRM
  • Ruta de acceso física: C:\inetpub\wwwroot\crm
  • Enlace (binding): lo configuras en el siguiente punto.

Equivalente por línea de comando:

& "$env:windir\system32\inetsrv\appcmd.exe" add site /name:"CRM" /physicalPath:"C:\inetpub\wwwroot\crm" /bindings:"http/*:8056:"

4.2 Binding HTTPS en el puerto 8056 con el certificado del dominio

El sitio debe atender HTTPS en el puerto 8056 con el certificado de dessti-aplicaciones.ddns.net.

Opción A — Let's Encrypt con win-acme (recomendado si el dominio es accesible):

  • Descarga win-acme y ejecútalo como administrador.
  • Elige crear un certificado para dessti-aplicaciones.ddns.net y enlazarlo al sitio CRM. win-acme instala el certificado y programa su renovación automática.
  • Ajusta el binding para que use el puerto 8056 (win-acme suele crear en 443; edítalo o créalo en 8056 según abajo).

Opción B — Certificado en archivo .pfx:

# Importa el .pfx al almacén del equipo (te pedirá la contraseña del pfx)
Import-PfxCertificate -FilePath "[RUTA_O_PFX_CERT]" `
  -CertStoreLocation Cert:\LocalMachine\My `
  -Password (Read-Host -AsSecureString "Contraseña del PFX")

Después, en IIS → sitio CRM → Enlaces… → Agregar: tipo https, puerto 8056, host dessti-aplicaciones.ddns.net, y selecciona el certificado importado.

TLS 1.2+ Configura Schannel de Windows para permitir solo TLS 1.2 o superior y deshabilitar SSL 3.0 / TLS 1.0 / 1.1. Ver la sección Seguridad.

4.3 (Opcional) Redirección HTTP → HTTPS

Si quieres que quien entre por HTTP sea llevado a HTTPS, agrega un binding HTTP y una regla de redirección a nivel de sitio. En el web.config de este paquete se incluye una regla de redirección comentada (desactivada) para no interferir con el proxy de ARR; actívala solo si comprendes su efecto.

4.4 Habilitar el proxy de ARR

Este es el interruptor que permite el reenvío de /api. En el Administrador de IIS: selecciona el nodo del servidor (raíz) → Application Request Routing Cache → Server Proxy Settings… → marca Enable proxy → Apply.

Sin ARR proxy no hay backend Si olvidas este paso, las llamadas a /api fallarán (típicamente 502/504). Es el error más común.

4.5 Firewall: abre 8056, no expongas 8080

# Permitir tráfico entrante HTTPS en el puerto público 8056
New-NetFirewallRule -DisplayName "CRM HTTPS 8056" -Direction Inbound `
  -Protocol TCP -LocalPort 8056 -Action Allow

# NO crear ninguna regla que abra el 8080: el backend es solo local.
Nunca abras el 8080 al exterior El backend escucha en 127.0.0.1:8080 y solo debe ser alcanzable por IIS en el mismo servidor. Exponerlo saltaría la terminación TLS y las cabeceras de reenvío.

Paso 5 Backend como servicio de Windows

Para que el backend arranque solo al reiniciar el servidor y se recupere ante fallos, instálalo como servicio de Windows. Este paquete incluye instalar-servicio-backend.ps1 y la plantilla parametros.example.ps1.

5.1 Prepara tus parámetros

  1. Copia la plantilla y renómbrala (sin «example»): 
    Copy-Item ".\parametros.example.ps1" ".\parametros.ps1"
  2. Edita parametros.ps1 y sustituye todos los [CORCHETES] por tus valores reales (rutas de Java y del jar, claves de BD, JWT, cifrado, emisor).

5.2 Instala el servicio

Opción recomendada — nssm (más simple y robusto para logs/reinicios). nssm es una utilidad externa (un único nssm.exe); descárgala de nssm.cc y colócala en el PATH o indica su ruta:

# En PowerShell como administrador, en esta carpeta:
.\instalar-servicio-backend.ps1 -Metodo nssm -NssmPath C:\tools\nssm.exe
# Si nssm.exe ya está en el PATH, basta:
.\instalar-servicio-backend.ps1 -Metodo nssm

Opción de respaldo — sc.exe (nativo de Windows, sin dependencias). El script genera un .cmd envoltorio y crea el servicio con sc.exe:

.\instalar-servicio-backend.ps1 -Metodo sc
nssm vs sc.exe nssm es la opción recomendada: gestiona bien el arranque, la detención, el reinicio ante fallos y la rotación de logs de un proceso Java. sc.exe funciona sin instalar nada, pero como java.exe no es un servicio nativo, el control de detención/reinicio es menos limpio.

5.3 Verifica que el backend responde localmente

# El servicio debe estar "Running"
Get-Service CRM-Backend

# El health check debe responder (desde el propio servidor)
Invoke-WebRequest http://127.0.0.1:8080/api/v1/actuator/health -UseBasicParsing

Revisa el arranque y los posibles errores en C:\apps\crm\logs\backend-stdout.log y backend-stderr.log.

Paso 6 Verificación de extremo a extremo

  1. Desde un equipo externo (o el mismo servidor), abre https://dessti-aplicaciones.ddns.net:8056. Debe cargar la pantalla de inicio de sesión del CRM y el candado del navegador debe indicar conexión segura.
  2. Inicia sesión como super_admin con [SUPERADMIN_LOGIN] / [SUPERADMIN_PASSWORD]. Si el login responde, IIS está enrutando /api al backend correctamente.
  3. Crea una empresa de prueba desde el panel de plataforma para confirmar que la escritura en la base funciona.
  4. Recarga (F5) estando en una ruta interna (p. ej. el listado de empresas): debe seguir funcionando, sin 404 (confirma el fallback de la SPA).

Checklist final

  • IIS en ejecución y sitio CRM iniciado.
  • ARR con Enable proxy activado.
  • Binding HTTPS en el puerto 8056 con el certificado del dominio.
  • Servicio CRM-Backend en estado Running y con arranque automático.
  • http://127.0.0.1:8080/api/v1/actuator/health responde en el servidor.
  • La SPA carga en https://dessti-aplicaciones.ddns.net:8056 con candado seguro.
  • Login de super_admin correcto (prueba que /api se enruta).
  • Recarga en una ruta interna no da 404 (fallback SPA).
  • Puerto 8080 NO abierto en el firewall.
  • Claves de producción (BD, JWT, cifrado) distintas de las de desarrollo.

Solución de problemas

Síntomas frecuentes y causas
SíntomaCausa probableQué revisar
502 / 504 al llamar a /api Backend caído o ARR proxy no habilitado. Verifica Get-Service CRM-Backend y el health en 127.0.0.1:8080. Confirma Enable proxy en ARR (Paso 4.4).
404 al recargar una ruta de Angular Falta la regla de fallback de la SPA. Confirma que web.config está en la raíz del sitio y que la regla «Fallback SPA» existe (Paso 3).
Error de conexión a la BD en el arranque Credenciales incorrectas o servicio de PostgreSQL detenido. Revisa Get-Service *postgres* y las claves en parametros.ps1. Mira backend-stderr.log.
Mixed content / llamadas a http La SPA está usando una URL absoluta en vez de /api. La base de API debe ser relativa (/api/v1, mismo origen). Verifica el build del frontend.
HTTP 500.19 al abrir el sitio Falta URL Rewrite/ARR, o MIME duplicado en web.config. Confirma que URL Rewrite y ARR están instalados. El web.config usa remove antes de add para evitar duplicados.
Login falla con token grande Cabecera Authorization muy larga. El backend ya amplía el límite a 64 KB por defecto; no requiere acción salvo casos extremos.

Seguridad

  • No expongas el 8080. El backend escucha solo en 127.0.0.1 y únicamente IIS lo alcanza. No abras ese puerto en el firewall.
  • Claves de producción. Genera JWT y llaves de cifrado nuevas para el servidor; no reutilices las de desarrollo. Restringe el acceso a parametros.ps1.
  • TLS 1.2+. Deshabilita SSL 3.0 y TLS 1.0/1.1 en Schannel; permite solo TLS 1.2 o superior con cifradores modernos.
  • Confianza en X-Forwarded-*. El backend confía en estas cabeceras solo porque está detrás de IIS y no es accesible directamente. Mantener el 8080 cerrado es lo que hace segura esa confianza.
  • Cabeceras de seguridad y CSRF. El backend emite CSP, HSTS, X-Frame-Options, Referrer-Policy y X-Content-Type-Options en cada respuesta, y es stateless con Bearer JWT (sin superficie CSRF clásica).
  • Cuenta del servicio. Ejecuta el servicio con una cuenta de privilegios mínimos y controla los permisos de C:\apps\crm.

Actualizaciones futuras

Nuevo build del frontend

  1. Genera el nuevo build y copia el contenido de dist\frontend\browser\* sobre C:\inetpub\wwwroot\crm (sobrescribiendo).
  2. Conserva el web.config existente (no lo borres al copiar).
  3. Refresca el navegador; los nombres de archivo llevan hash, así que el navegador tomará la versión nueva.

Nuevo jar del backend

# 1) Detener el servicio
Stop-Service CRM-Backend

# 2) Reemplazar el jar
Copy-Item ".\crm-0.0.1-SNAPSHOT.jar" "C:\apps\crm\backend\" -Force

# 3) Iniciar el servicio (Flyway aplicará nuevas migraciones al arrancar)
Start-Service CRM-Backend

# 4) Verificar
Invoke-WebRequest http://127.0.0.1:8080/api/v1/actuator/health -UseBasicParsing
Respaldo antes de actualizar Antes de una actualización que incluya nuevas migraciones, respalda la base dessti_plataforma (p. ej. con pg_dump). Así puedes revertir si algo sale mal.
