## CORRECCIONES al TRASPASO.md anterior (importantes)

1. **Tests del frontend usan VITEST, no Jasmine.** El traspaso viejo decía "jsdom+TestBed,
   NUNCA vitest"; en la práctica `npx ng test` arranca **Vitest**. Consecuencia real:
   los matchers deben ser de Vitest: usar `expect(x).toBe(true)` (NO `toBeTrue()`),
   `toEqual`, `toContain`, `toBeInstanceOf`. Comando que funciona:
   `npx ng test --watch=false --include="<ruta-al-spec>"`.

2. **JDK: hay que compilar y PROBAR con JDK 21, aunque la máquina tenga JDK 25.** Con
   JDK 25: (a) Lombok 1.18.34 rompe la compilación (`ExceptionInInitializerError:
   com.sun.tools.javac.code.TypeTag :: UNKNOWN`); (b) **Mockito (inline mocks) no
   puede instrumentar clases**, por lo que los tests `@WebMvcTest` fallan con
   `Failed to load ApplicationContext` / `Mockito cannot mock this class`.
   **OJO (2026-09-24):** la extensión de Java de Kiro (`pleiades java-extension-pack`)
   deja el `JAVA_HOME` GLOBAL apuntando a un JDK 25:
   `C:\Users\<user>\AppData\Roaming\Kiro\User\globalStorage\pleiades.java-extension-pack-jdk\java\25`.
   Por eso Maven/`mvnw` toman JDK 25 por defecto y los tests de controller fallan
   aunque el código sea correcto. Solución: fijar `JAVA_HOME` al JDK 21 antes de
   cualquier build/test (usar el script `local-dev\_build-backend-local.cmd`, que lo
   hace solo), o cambiar la variable de usuario `JAVA_HOME` de Windows a
   `C:\Program Files\Java\jdk-21.0.12` de forma permanente. El síntoma se distingue
   fácil: los tests de DOMINIO puros (p. ej. `PlanVsSuscripcionDominioPropertyTest`)
   PASAN, y solo fallan los `@WebMvcTest` con Mockito → es entorno, no código.

3. **`-o` (offline) de Maven solo funciona si `.m2` ya está poblado.** En una máquina
   nueva, el PRIMER build/test de backend debe ser ONLINE (sin `-o`) para descargar
   plugins (incl. `surefire-junit-platform`). Después ya se puede usar `-o`.

4. **La terminal de la sesión duplica el eco de caracteres** y a veces reporta exit
   code -1 aunque el comando SÍ corre. Estrategia fiable: volcar salida a un archivo
   `_*.txt`/`_*.log` y leerlo. Estos temporales están en `.gitignore`.

  (1 col móvil / 2 desde 'sm'), `ds-form__field(--full)`, `ds-form__help` (texto de ayuda
  FUERA del subscript de Material, evita solapamientos), `ds-form__note(--warn/--info)`,
  `ds-form__summary(-info/-conteo/-etiqueta/-total)` (order summary con total en vivo).
- **`shared/components/selectable-card/`** (`app-selectable-card`): tarjeta seleccionable
  animada que sustituye checkboxes "planos". `@Input seleccionado/deshabilitado`,
  `@Output seleccionadoChange` (boolean), role=checkbox, teclado Espacio/Enter, micro-pulso
  al seleccionar. Se usa para módulos de plan/paquete/empresa y roles de usuario.
- **`shared/components/operacion-overlay/`** (`OperacionOverlayService`): overlay central
  animado de operaciones. API:
  `overlay.ejecutar(observable, { tipo, textoProceso, textoExito, duracionExitoMs? })`
  que REEMITE el observable (next/error/complete intactos). Fase proceso: spinner + halo +
  ícono contextual; fase éxito: check SVG dibujado (stroke-dashoffset) + destello. Íconos
  por tipo: guardar=save, crear=add_task, procesar=sync, traspasar=sync_alt, eliminar=delete.
  Respeta prefers-reduced-motion. Se monta solo en el <body> vía createComponent (providedIn root).
- **`styles/_tokens.scss`**: se añadieron `--ds-easing-emphasized` (rebote sutil) y
  `--ds-easing-decelerate` (salidas que se disipan), además del ya existente `--ds-easing-standard`.

## Patrón de uso (para futuros formularios/diálogos)
1. Layout: envolver el `<form class="ds-form">` con header (`ds-form__header`) y secciones
   two-pane (`ds-form__section` → aside + body con `ds-form__grid`).
2. Selección múltiple: `app-selectable-card` en rejilla `repeat(auto-fill, minmax(220px,1fr))`.
3. Guardado/acción: envolver la petición HTTP:
   ```ts
   this.overlay.ejecutar(this.service.guardar(cmd), {
     tipo: esEdicion ? 'guardar' : 'crear',
     textoProceso: 'Guardando…', textoExito: 'Guardado',
   }).subscribe({ next, error });  // conservar toast/signals existentes
   ```
   En métodos async tras `ConfirmDialogService`, el overlay envuelve SOLO la llamada
   posterior al `await` (early-return si el usuario cancela).
4. Diálogos two-pane: abrir con `width/maxWidth: 'min(920px, 96vw)'` (o 760/860 según
   densidad) + `panelClass: 'ds-dialog-panel'`.

## Comportamiento vs. tests (IMPORTANTE)
`OperacionOverlayService.ejecutar` emite `observer.next` SÍNCRONAMENTE dentro del `complete`
del observable origen (el timeout solo controla cuánto se ve la animación de éxito). Por eso
los specs que hacen `req.flush(...)` y luego comprueban `dialogRef.close`/`cerradoCon` o
`expectOne` SIGUEN pasando sin cambios: el cierre/efecto ocurre síncrono tras el flush.
